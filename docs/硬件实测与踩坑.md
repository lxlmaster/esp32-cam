# 硬件实测与踩坑记录

这份文档记录从「板子到手」到「手机能看画面」全过程中所有实测数据和踩过的坑。踩坑部分按遇到顺序排，每条都写了现象、原因和解法。

---

## 一、硬件实测

板子是闲鱼 ¥44 的 ESP32-S3-CAM（幻尔 Hiwonder 套件，附完整资料包）。所有数据均为实测，与卖家描述不一致的地方已标注。

### 芯片

```
Chip type : ESP32-S3 (QFN56)  revision v0.2
Features  : Wi-Fi, BT 5 (LE), Dual Core + LP Core, 240MHz, Embedded PSRAM 8MB (AP_3v3)
Crystal   : 40MHz
MAC       : e0:72:a1:d0:00:8c
```

### Flash 与 PSRAM

```
Manufacturer: 20   Device: 4017
Detected flash size: 8MB        <- 卖家标 N16R8，实测是 N8R8
Flash type set in eFuse: quad (4 data lines)
PSRAM: 8MB（封装内置）
```

**影响**：板子设置里 Flash Size 必须选 8MB。选 16MB 会让分区表与实际不符，烧完直接起不来。

不过对摄像头项目影响不大 —— 固件本身约 1MB，8MB 完全够用。

### 摄像头

```
PID  = 0x2145
VER  = 0x00
型号 = GC2145（GalaxyCore 格科微，UXGA 1600x1200）
SCCB 地址 = 0x3C（8 位地址 0x78）
```

资料包里的 `4.技术参数&原理图/2.摄像头GC2145.pdf` 是 45 页官方规格书，证实板上就是 GC2145 —— **卖家没有虚标**。

### 引脚（官方 ESP32S3-EYE 定义）

与 Freenove 公版接法完全一致：

| 功能 | GPIO | 功能 | GPIO |
|---|---|---|---|
| XCLK | 15 | D0 (Y2) | 11 |
| SIOD (SDA) | 4 | D1 (Y3) | 9 |
| SIOC (SCL) | 5 | D2 (Y4) | 8 |
| PCLK | 13 | D3 (Y5) | 10 |
| VSYNC | 6 | D4 (Y6) | 12 |
| HREF | 7 | D5 (Y7) | 18 |
| PWDN | -1 | D6 (Y8) | 17 |
| RESET | -1 | D7 (Y9) | 16 |

官方参数补充：**XCLK 用 15MHz**（不是常见的 20MHz），`grab_mode = CAMERA_GRAB_WHEN_EMPTY`。

## 二、环境搭建的坑

### 坑 1：官方板包索引在国内连不上

**现象**：按官方教程在板管理器里填 `https://raw.githubusercontent.com/espressif/arduino-esp32/gh-pages/package_esp32_index.json`，进度条永久卡住。

**原因**：`raw.githubusercontent.com` 在国内基本不可达（实测超时 15s 无响应）。

**解法**：改用乐鑫官方中国 CDN：

```
https://dl.espressif.cn/dl/package_esp32_index.json
```

实测响应 **0.13 秒**，比官方源快一个数量级。能装到的版本也很新（esp32:esp32@3.3.12）。

### 坑 2：CH340 驱动 Windows 没自带

**现象**：板子插上后设备管理器里出现 `USB Serial`，状态是「错误」，错误码 Code 28。串口列表里看不到任何新端口。

**原因**：板子用 CH340 做 USB 转串口（`VID_1A86` / `PID_7523`），Windows 不自带这个驱动。

**解法**：装 WCH 官方驱动。注意要用有 WHQL 签名的版本，装完签名验证应该是：

```
CH341SER.CAT    Valid    CN=Microsoft Windows Hardware Compatibility Publisher
CH341S64.SYS    Valid    CN=Microsoft Windows Hardware Compatibility Publisher
```

安装需要管理员权限（`pnputil /add-driver CH341SER.INF /install`）。

### 坑 3：GitHub raw 不通，下载驱动绕路

`raw.githubusercontent.com` 不通，但 `api.github.com` 和 `github.com/releases` 是通的。下载单个文件可以走 API 的 raw 通道：

```bash
curl -H "Authorization: Bearer $TOKEN" \
     -H "Accept: application/vnd.github.raw" \
     "https://api.github.com/repos/USER/REPO/contents/path/file" -o file
```

## 三、编译与烧录的坑

### 坑 4：USB CDC On Boot 必须关（最容易误判成板子坏了）

**现象**：程序烧录成功，哈希校验通过，但串口监视器**一片空白**，什么都打不出来。

**原因**：`USB CDC On Boot = Enabled` 时，Arduino 会把 `Serial` 重定向到 ESP32-S3 的原生 USB 接口。而这块板的数据是从 **CH340 → UART0** 出来的，原生 USB 根本没引出。结果就是程序正常跑、日志却全丢了。

**解法**：`USB CDC On Boot = Disabled`。

### 坑 5：`sensor_t` 的成员叫 `pixformat` 不是 `pixel_format`

编译报错：

```
error: 'sensor_t' has no member named 'pixel_format'; did you mean 'pixformat'?
```

### 坑 6：bash 管道会吃掉退出码

```bash
arduino-cli compile ... | grep xxx; echo $?    # 永远是 0，因为 $? 是 grep 的
```

编译失败也返回 0，会误以为成功。正确写法：

```bash
arduino-cli compile ... > log 2>&1; echo "EXIT=$?"; grep xxx log
```

### 坑 7：官方预编译固件配不上新 bootloader

资料包里有厂家调好的 `image_transmit.bin`（1.25MB，app-only 镜像），烧到 `0x10000` 后无限重启：

```
E (25) esp_image: Segment 0 0x3fce3810-0x3fce3cf4 invalid: overlaps bootloader stack
E (26) boot: No bootable app partitions in the partition table
```

**原因**：该固件基于 ESP-IDF 4.x 编译，段加载地址与 IDF 5.x 的 bootloader 栈区域冲突。资料包只给了 app bin，没给配套 bootloader，所以没法直接用。

## 四、GC2145 驱动的真相（重点）

### 为什么一开始误判成「驱动缺失」

用 `PIXFORMAT_JPEG` 初始化时报：

```
E camera: JPEG format is not supported on this sensor
错误码 0x106 (ESP_ERR_NOT_SUPPORTED)
```

第一反应是「引脚错了」或「驱动没有这个 sensor」。但报错是「不支持 JPEG」而不是「找不到摄像头（0x105）」，说明 **SCCB 通信是通的、芯片已经认出来了**，只是它没有 JPEG 能力。

### 确认支持，但接口是空壳

查 `libesp32-camera.a` 符号，GC2145 有 66 处引用（和 gc0308/gc032a 同量级），确认驱动**存在**。

但读 `sensors/gc2145.c` 源码发现：

```c
sensor->set_contrast   = set_dummy;
sensor->set_brightness = set_dummy;
sensor->set_saturation = set_dummy;
sensor->set_sharpness  = set_dummy;
sensor->set_denoise    = set_dummy;
sensor->set_quality    = set_dummy;
sensor->set_whitebal   = set_dummy;    // 白平衡
sensor->set_awb_gain   = set_dummy;
sensor->set_gain_ctrl  = set_dummy;
```

`set_dummy` 就是 `return 0`，**什么都不做**。

真正实现的只有：

```c
set_pixformat, set_framesize, set_vflip, set_hmirror, set_colorbar, get_reg, set_reg
```

而且 `init_status` 里直接写死：

```c
sensor->status.awb = 0;      // 声明「不支持自动白平衡」
sensor->status.awb_gain = 0;
```

**这意味着所有靠 API 调白平衡/亮度/对比度/饱和度的代码全是空转。**

### 但硬件本身有 AWB/AEC

GC2145 规格书里这些功能齐全：

| 功能 | 寄存器 |
|---|---|
| AWB 参数 | `P1:0x50 ~ 0x7e` |
| AWB R/G/B 增益（只读） | `P0:0xb3 / 0xb4 / 0xb5`（默认 0x40 = 1.0×） |
| AEC 抗闪烁步长 | `P1:0x25 / 0x26`（默认 360） |
| 曝光值 | `P0:0x03 / 0x04` |

而且**实测关灯后画面会自动提亮** —— 说明 GC2145 内部固件自带 AEC，不依赖驱动接口。

### 唯一可用的后门：set_reg

`set_reg` 是真实现的，可以直接写寄存器：

```c
s->set_reg(s, 0xFE, 0xFF, page);   // 先切页（P0=0, P1=1, P3=3）
s->set_reg(s, 0x51, 0xFF, 0x80);   // 再写目标寄存器
```

限制：寄存器地址只有 8 位，GC2145 的 P0/P1 分页必须靠写 `0xFE` 手动切。

## 五、色彩校正：一次典型的「动手太快」

### 现象

画面整体偏绿。

### 我的错误做法

看到偏绿，没做对照，直接定了压绿参数写进默认值：

```c
g_rGain = 256;   // 1.00×
g_gGain = 205;   // 0.80×  压绿
g_bGain = 275;   // 1.07×  提蓝
```

结果画面变成**紫红色 + 青蓝色噪点**，比原来更糟。

### 正确做法

**先关掉校色看原始画面**：

```
/set?cf=0
```

关掉后发现 —— **原始画面本来就是正常的**。只是暗光环境下有点轻微灰绿感，完全在可接受范围。

绿被压到 0.8 倍后，红相对突出，于是整体偏红紫。

### 最终方案

```c
g_rGain = 256;
g_gGain = 256;
g_bGain = 256;
g_colorFix = false;   // 默认不校色
```

代码保留（查表 LUT 实现），需要时可用 `/set?rg=&gg=&bg=` 实时调。

**教训：没看到「改之前」的样子，不该动手改。任何校正前先抓一张基线图。**

## 六、性能优化

### 起点：串行架构只有 4fps

最初的固件把「抓帧 → 压缩 → 发送」全放在 HTTP handler 里，一次请求 224-254ms。

瓶颈在于这三步是串行的，而且 HTTP 请求在处理期间不能做别的。

### 关键优化：改成生产者-消费者流水线

```
camTask（钉在 Core 1）：
    循环 { 抓帧 → frame2jpg → 写共享缓冲 }
HTTP handler（跑在 Core 0）：
    从共享缓冲 memcpy 一份就走
```

效果：

| 架构 | 480×320 抓图耗时 |
|---|---|
| 串行 | 224-254ms |
| 流水线 | **75-130ms** |

**同样的分辨率，速度接近翻倍。**

### 第二个优化：色彩校正改用查表

原来逐像素做 3 次乘法 + 3 次 clamp 分支，改成预计算 128 项 LUT：

```c
p[i] = (rLUT[(v>>11)&0x1F] << 11) | (gLUT[(v>>5)&0x3F] << 5) | bLUT[v&0x1F];
```

400×296 的压缩耗时从 124ms 降到 100ms。

### 附带发现：JPEG quality 不影响速度

| quality | 压缩耗时 | 文件大小 |
|---|---|---|
| 10 | 153ms | 9.3KB |
| 14 | 155ms | 12.3KB |
| 18 | 158ms | 14.8KB |
| 22 | 160ms | 17.4KB |

quality 从 10 调到 22，耗时只增加 7ms，但文件大小翻倍。说明 `frame2jpg` 的耗时主要是固定开销（色彩空间转换、DCT），跟量化步长关系不大。

**结论：调 quality 既省不了时间，也换不来速度，别在这上面浪费时间。**

### 最终配置

```
400×296 / quality 10 / 无校色  →  100ms/帧 = 10.0fps
```

## 七、假故障：代理导致 Debug 一小时

### 现象

```
ping 192.168.1.15 → 8 个包丢 5 个（62%），延迟 496ms / 1172ms
抓图 → 6.9 秒一张，连续 5 张里 3 张超时
```

第一反应是 WiFi 信号差或者供电不足。

### 真实原因

用户开着 Clash 的 TUN 模式。`192.168.1.15` 是私有地址，本不该走代理，但 TUN 会劫持所有流量（连 ICMP 都不放过），塞进隧道绕一圈。

### 验证与修正

关掉代理后：

```
ping  → 6 个包 0 丢包，延迟 5-84ms
抓图  → 104-248ms，稳定
```

**排查局域网设备时，第一件事是关掉所有代理和 VPN。** HTTP 请求可以加 `--noproxy '*'` 绕过，但 ping 走 ICMP，绕不过 TUN。

## 八、未解决的问题

### 光波（横向滚动条纹）

现象：画面出现一条条横向明暗带，缓慢滚动。

原因：**rolling shutter banding**。CMOS 是逐行曝光的，如果光源有频闪（LED 用 PWM 调光极常见），不同行曝光时的亮度就不一样，形成条纹。

GC2145 本来有抗闪烁机制 —— 靠 `P1:0x25/0x26` 的 AEC anti flicker step 把曝光时间锁到电源周期（50Hz → 20ms 的整数分之一）。但它依赖 AEC 正常工作，而 AEC 的接口又是 `set_dummy`。

**排查方法**（未完成）：

1. 开灯，镜头对白墙（平整表面条纹最明显）
2. 抓图后逐行算平均亮度，如果有规律起伏就是频闪
3. 换白炽灯/卤素灯（热惯性，不闪）再测。条纹消失 = 灯的锅；依然有 = 相机或电源问题

**可能的解法**：用 `/set?reg=` 直写 AEC 寄存器手动锁曝光。

### 镜头对焦

画面明显发虚。GC2145 模组的镜头是**螺纹的**，出厂是松的，需要手动旋转调焦。

调焦技巧：分辨率切到 640×480，对着有文字的物体，慢慢转镜头，转到文字边缘最锐利停下，再切回 400×296。

## 九、走不通的路（避免重复投入）

### 用第二块板子做「外挂算力」

手上有两块同型号 S3-CAM，用杜邦线连了 `5V/GND/SDA/SCL`（这是 I2C）。

**不可行**，两个原因：

1. **I2C 带宽太低**：400kHz 快速模式 = 50KB/s。传一帧 RGB565 300KB 要 **6 秒**。
2. **数据量悖论**：想让 B 板帮忙压缩，得先把 300KB 原始帧传过去（120ms+），而 A 板自己压只要 100ms。**传过去再压比自己压还慢。**

正确用法是**两路独立监控**（两个 IP、两个页面、两个角度）。

⚠️ **安全提醒**：两块板都插 USB 时，必须拔掉连接 5V 的那根线，否则两个 5V 源互相对灌。

### 调 JPEG quality 提速

见第六节，耗时几乎不变。

### 用 set_colorbar 验证通道

`set_colorbar` 虽然在驱动里有实现，但实测没生效（画面还是实景，没出彩条）。

不过那次测试反而证实了更重要的事：画面里白色物体是白的（不是蓝的），说明 **RGB 通道顺序和字节序都是对的**。
