# 性能优化与移动抓拍

## 本次代码修改

- 用 `frame2jpg_cb` 直接编码到固定 PSRAM 缓冲，通过交换指针发布帧，去掉原来的每帧 JPEG 输出缓冲分配和发布时整帧复制。编码器内部仍会分配工作内存。
- `/snap` 与 MJPEG 各有独立的固定发送缓冲，读取长度、帧序号、内容时持有同一把锁，修复原来先读取长度再分配导致的越界风险。
- 网页使用 `/snap?after=<帧序号>`；没有新帧返回 204，按采集速度限制轮询，减少重复传输。
- 使用 `CAMERA_GRAB_LATEST`，处理较新的帧，优先减少延迟。它不能提高软件编码器本身的速度。
- 摄像头采集、重建、传感器设置、色彩查表更新共用互斥锁，去掉固定延时等待采集停止的做法。
- MJPEG 移到 `http://<IP>:81/stream`，避免长连接占住 80 端口上的控制、抓图和状态接口。当前支持单路 MJPEG 客户端。
- 修正软件 JPEG 质量参数：范围 **1–100，越大越清晰，默认 75**。旧文档的 0–63 是硬件 JPEG 参数，不能用于 `frame2jpg`。质量变化只更新软件编码参数，无需重启摄像头。提高画质可能增加编码时间和网络流量，不能直接与旧的质量 10 比较帧率。
- 软件色彩校正按摄像头 RGB565 的高字节在前布局处理，修复原来小端 `uint16_t` 访问时的颜色错误。

固定 JPEG 缓冲每个 256 KiB：两个编码/发布槽、两个 HTTP 发送槽、一个事件照片槽，合计 1.25 MiB PSRAM。推送最多保留一个正在发送、一个排队事件，每个最多再占 256 KiB。编码超出槽容量会丢弃该帧，避免越界或发送截断 JPEG。

## 检测模块与算法接入

`firmware/esp32_cam_final/motion_detector.h` 不依赖 Arduino 和网络。

入口是 `MotionDetector::update(rgb, len, width, height, uptimeMs)`，返回 `true` 即触发事件；`score()` 提供最近一次检测的变化百分比。采集任务在校色前调用它，检测的原始图像与事件 JPEG 来自同一帧。自行编写算法时替换 `update()`；不要在算法里进行 HTTP、延时或另行调用摄像头。

默认算法：

1. 在原始 RGB565 图像上取 32×24 共 768 个采样点并转亮度，无需复制或解码 JPEG。
2. 最短 200 ms 检测一次，与上一次采样比较，补偿全局平均亮度变化。
3. 单点亮度差达到 24，计为变化；变化点至少占 12%，计为有效变化。
4. 连续 2 次有效变化触发一次抓拍；触发后 15 秒冷却。

参数位于 `MotionConfig`。可在主固件 `motionConfig()` 中调整 `sampleIntervalMs`、`pixelThreshold`、`changedPercent`、`confirmations`、`cooldownMs`，重编译生效。分辨率变化后重新建立基准，不把重启后的首帧当作运动。

这是移动变化检测，不包含人/动物识别、运动方向判断或精确越线计数。快速掠过、很远的小物体可能漏检，树叶、阴影和局部灯光变化可能误报。需要按安装位置调参；连续确认意味着物体必须在至少两个采样间隔内持续产生变化。

## 抓拍与推送

复制同目录 `config.example.h` 为 `config.local.h`（已由 Git 忽略）：

```cpp
#pragma once
#define MOTION_ENABLED true
#define MOTION_WEBHOOK_URL "http://192.168.1.10:8080/camera"
#define MOTION_WEBHOOK_TOKEN "替换为接收端令牌"
#define MOTION_WEBHOOK_CA ""
```

推送目标默认留空；即使不配置推送，也会在内存保留最近一次事件照片。`MOTION_ENABLED=false` 可关闭检测。所有配置变更都需要重新编译、烧录。

`motion_events.cpp` 在独立的低优先级任务里发送请求，不在采集线程里等待网络。接收协议：

```http
POST /camera
Content-Type: image/jpeg
Authorization: Bearer <配置的令牌，仅非空时发送>
X-Camera-Event: <本次启动内递增的事件序号>
X-Camera-Uptime-Ms: <触发时设备运行毫秒数，非日期时间>
X-Motion-Score: <变化百分比>

<JPEG 二进制>
```

返回任意 2xx 视为成功。连接超时 3 秒、读取超时 5 秒、TLS 握手超时 5 秒。队列满时丢弃新推送并计数，最近抓拍仍更新。网络失败计入失败数，当前不自动重试、不持久化、不保证送达。照片与事件序号在重启后清空。

HTTPS 必须通过 `MOTION_WEBHOOK_CA` 配置受信任根 CA 的 PEM 文本；不会跳过证书校验。首次 HTTPS 推送会启动 SNTP 时间同步，尚未同步时本次发送记为失败（`last_http=-5`）；缺少 CA 时为 `-2`。部署时确保设备可以访问时间服务器。不要把含密钥的 `config.local.h` 提交到 Git。

微信公众号、企业微信、飞书、Telegram 等平台一般不能直接接收这种 JPEG 请求；需要对应平台适配或一个接收服务，把照片转成平台要求的上传及消息接口。

## HTTP 接口

以下接口均沿用摄像头的 Basic Auth：

| 接口 | 用途 |
| --- | --- |
| `GET /motion` | 检测开关、事件数、最近变化分数、照片大小、发送成功/失败/丢弃数、最后 HTTP 状态 |
| `GET /motion/photo` | 最近事件照片；尚无照片时 404 |
| `GET /snap` | 当前预览 JPEG；尚无帧时 204 |
| `GET /snap?after=123` | 帧序号与 123 相同则 204，否则返回 JPEG 与 `X-Frame-Id` |
| `GET /set` | 预览状态，质量范围变为 1–100 |
| `GET :81/stream` | 独立端口 MJPEG，播放器需要使用 81 端口 |
